# Agent wallet 0.1: design

Status: working version for Windows, 11 October 2026. Code and install steps: [wallet/](../wallet/README.md).

The wallet is the visitor's side of BYOA. 0.1 is the first one that runs: a page asks for the visitor's AI, the visitor allows it in a short consent window, and the page's speech clips and text prompts are handled by the visitor's own models. A site reaches it through the browser extension or, with no extension, through a `bringyourownagent://` link and the wallet's own connection to the site's server (section 10). It follows the consent flow of the vision ([3.1](vision.md#31-the-consent-flow-proposed)) and checks every call with the draft rules ([spec/rules-0.1-draft.md](../spec/rules-0.1-draft.md)) through the .NET library before any model runs.

## 1. Architecture

```
web page ── window.byoa ──▶ page.js (MAIN world)
                               │ window.postMessage
                            bridge.js (isolated world): judges the click from navigator.userActivation
                               │ chrome.runtime.sendMessage
                            background.js (service worker): adds the origin from Chrome's sender, top frames only,
                               │ timeouts, passes back only the contract's shapes
                               │ native messaging (stdio: 4-byte little-endian length + UTF-8 JSON)
                            byoa-host.exe: relays frames, starts the wallet for a request
                               │ named pipe, per user (CurrentUserOnly), same framing
                            Byoa.Wallet.exe (tray): engine ─▶ gate (BringYourOwnAgent) ─▶ route ─▶ source
                                                      │                         programs on this PC (Llama, LM Studio, Ollama) · OpenRouter
                                                      └─ notice, consent window, settings, activity
```

- **Extension** (Chrome MV3, `wallet/extension`). Its ID is fixed by a `key` in the manifest (`niobopdoiopjilmlonjcgllpmgjemhpk`). It injects `window.byoa` into every `https://` page and into `http://localhost` and `http://127.0.0.1` pages, at `document_start`, and dispatches `byoa:ready`. It shows nothing of its own except the toolbar popup: wallet connected or not running, the versions, and a button that opens the wallet.
- **Native host** (`byoa-host.exe`, .NET 10). A relay with no decisions: it forwards frames as they are, answers the fallback when the wallet is not there (also when its pipe breaks or was already closed under it: the host keeps running and connects again on the next message), and starts the wallet only for a `request` (or the popup's `open`). It is registered for the current user only.
- **Wallet** (`Byoa.Wallet.exe`, .NET 10 and Avalonia 11). A tray app with one instance per user (a mutex) that serves the pipe. Its engine is a UI-free library (`Byoa.Wallet.Core`) with unit tests. Each connection can handle independent messages, while the site keeps at most four calls in flight and may queue a bounded number; the wallet refuses a fifth call as a backstop. The native pipe still applies its own bounded backpressure.

## 2. Messages

### Page API (CONTRACT 0.1)

```js
window.byoa.version                                     // "0.1"
await byoa.request(manifest)                            // { grantId, skills, expiresAt } | null
await byoa.call(grantId, "audio.transcribe",
                { audio: { mime: "audio/wav", base64 } },   // 16 kHz mono 16-bit PCM WAV, up to 15 s
                { language: "ru" })                     // { ok: true, output: { text }, receipt: { cost: "0.000 USD", provider: "local" | "home-server" | "api-key" } } | { ok: false }
await byoa.call(grantId, "text.generate",
                { messages: [{ role: "user", content: "Answer briefly." }] },
                { maxTokens: 128 })                       // same result shape; text is in output.text
await byoa.release(grantId)
```

`window.byoa` is a frozen, non-writable property. `null` and `{ ok: false }` are the only "no", whatever the reason.

### Extension, host and wallet

One JSON message per frame: `{ "id": n, "type", "origin", "userActivation", "payload" }`, answered by `{ "id": n, "result" }`.

| type | sent by | payload | result |
|---|---|---|---|
| `request` | a page | `{ "manifest": {...} }` | a grant or `null` |
| `call` | a page | `{ "grantId", "skill", "input", "params" }` | `{ "ok": true, "output", "receipt" }` or `{ "ok": false }` |
| `release` | a page | `{ "grantId" }` | `null` |
| `status` | the popup | `{}` | `{ "running": true, "version", "quiet" }`; from the host when the wallet is not running: `{ "running": false }` |
| `open` | the popup | `{}` | `{ "opened": true }` (starts the wallet if needed and opens its window) |

`origin` is set by the service worker from `sender.origin` (top frame of a tab, https or localhost); `userActivation` by the isolated-world script, only for `request`. `status` and `open` are additions for the popup; pages cannot send them. Frames from the browser are limited to 8 MB, frames to the browser to 1 MB (Chrome's limit). Timeouts in the service worker: request 125 s (the wallet itself gives up after 120 s), call 90 s.

## 3. What happens on a request

1. The origin must be `https://host[:port]`, or `http://localhost` / `http://127.0.0.1` for tests. The manifest must be valid under the draft rules (`Manifest.Validate`).
2. A **blocked** site gets `null` at once; no notice, ever.
3. If the site is **allowed with "decide on my own"** and the manifest asks for nothing new (no new skill the wallet can serve, no required skill it cannot serve, the expected cost per session not above the visitor's budget for the site), the wallet grants a page's request silently, click or no click, once the models are loaded (item 6). A direct link always asks, even then (CONTRACT-DIRECT.md §3).
4. **Without a click** anything else gets `null`; the tray icon gets a quiet dot and the site's count of held-back requests goes up. A page may make 30 such requests a minute; the rest get `null` and are not written down (one activity line says so), so a loop in a page costs the wallet nothing.
5. **With a click**: the notice, then the consent window. A second request from the same origin while the first is asking shares its answer; the question stays open while any page that asked still waits for it (closing the first tab does not close it for the second). One prompt is shown at a time. With no answer in 120 s the page gets `null`.
6. **Allow** stores the site's decision (skills, budget per session, "decide on my own", the expected cost and the languages) and opens a session grant: a random 144-bit id, valid 12 hours, held in memory only (a restarted wallet ends all sessions; the page then asks again). **The page gets its grant only when the models are ready**: the wallet asks the first local source of the route for each language the manifest declares to load its model (the program on this PC loads it; the wallet sends one short silent clip, or one short question, and keeps nothing from the answer) and waits for it, with "Preparing your model…" in a small toast meanwhile (shown only when it takes more than 150 ms). If that source fails, the next local source gets the chance. A preparation wait is capped at 30 s; after that the grant is answered and a ready fallback or the normal "AI unavailable" route decides the first call. The silent grant of item 3 waits the same way, without a toast. The wallet also asks for the models of the allowed sites when it starts. A slow preparation holds this site only; other sites continue to run.
7. **Asking for more** (a new skill the wallet can serve, a required skill it cannot serve, or an expected cost per session above the visitor's budget) shows only the difference: an "updated" chip, "Only what is new", and "Budget $0.05 → $0.10 per session" (from the visitor's budget to the site's new expected cost). A required skill no source can serve is shown as missing and Allow is not offered, so the page gets `null`; it is never granted silently. A higher expected cost that is still within the visitor's budget asks nothing.

## 4. What happens on a call

1. The grant must exist and belong to the calling origin, and the site must still be allowed.
2. The clip is decoded and measured by the wallet (`clipSeconds` from the WAV data, never from the page). PCM 8/16/24/32-bit and float WAVs at any common rate, mono or stereo, are accepted and converted to 16 kHz mono.
3. The wallet's own per-day limits: calls per site per day; money per site per day and for the whole wallet (paid sources only). Calls still running count too: a call holds its slot, and a paid source its estimate, from its start to its end, so many calls at once cannot pass a daily limit before the first one is logged.
4. The **route**: the skill's chain in the visitor's order, keeping sources that are switched on, available and know the call's language (`params.language`, or the only language the manifest declares). For each source in turn:
   - the **gate**: `Gate.CheckCall(manifest, grant, call, state)` with the provider kind (`local-model`, `home-server` or `api-key`), the estimated cost and the measured clip or text size; the slot and the estimated cost are reserved in the session state under a per-grant lock;
   - `blocked` (expired, clip too long, rate over the manifest's limit, skill not granted, …) ends the call with `{ ok: false }`; `not-local` moves on to the next source; `ask` (over the budget per session) moves on and, if nothing else can answer, ends with `{ ok: false }` and one notice that the site reached a limit;
   - a paid source with "ask before paid" asks the visitor (Allow once, Always for this site, No; no answer in 60 s is No);
   - a speech source runs for at most 45 s; a text source and the complete text route get the visitor's wait limit for the site (300 s unless he changed it, at most 600 s; the extension's call timeout is 610 s), and a call for one named model waits in line for its own source instead of moving on. The caller's cancellation is passed through. A failure releases only a genuinely unknown reservation; a paid response with a known or missing cost is settled using the reported cost or the estimate, and the next source is tried.
5. The activity log records the call: time, site, skill, clip length, language, the source that answered, the fallback route when the first choice did not answer, the cost and the time the source took. Never the audio or the text.

Receipts give the cost with at least three decimals and `provider` as `local`, `home-server`, or `api-key`; the page never learns which model answered.

## 5. The manager's suggestion

0.1 has no AI manager. The consent row and the Skills page explain the route from the sources' properties (`languages`, `runs`, measured seconds per clip, cost). A speech model the visitor added (a model in the Llama app, LM Studio, Ollama or another OpenAI-compatible program) comes first, then the paid source, which is last and asks first. A source whose program is not running is skipped with the reason "not running". The wallet holds no model, so a new wallet's speech route is the paid source alone until the visitor adds a model.

## 6. Measured on the development machine (RTX 5080 Laptop, 16 GB)

The wallet holds no model, so these are the speeds of the programs it hands the request to, and what the hand-over adds (the wallet's own part is a few milliseconds).

| Source | Typical time inside the wallet | Notes |
|---|---|---|
| Qwen3-ASR 1.7B FP16 in the Llama app, on the GPU | 0.1-0.9 s per clip (183-335 ms from the site's server over a link, for Russian words and phrases) | Russian: 8 of 8 single words exact, phrase word error rate 0.00 in the wallet's end-to-end run; on the 96 synthetic clips of text-generate.md section 6, 19 of 24 words and 10 of 12 phrases. Slovak is weak (0 of 8 words exact): a model that hears Slovak better would have to be added for it |
| The same model, the first request after the program starts | about 75 s once | The program loads the model on demand; the wallet's warm-up clip (and the Test button) pays for it, so a site's first call is not the one that waits |
| Scribe v2 through OpenRouter | 0.6-1.7 s | about $0.00006 for a 2 s word |

From Allow to `request()` resolved, with the model already loaded in the program (the extension end-to-end run; the Russian and Slovak clips came after it): Allow to grant 2.4 s, which includes the 0.4 s the warm-up took, and the first call after the grant took 0.19 s (Russian) and 0.11 s (Slovak). Through a link, with the wallet starting cold: Allow to the site's `hello` 4.7 s, then 183-335 ms per call.

## 7. What 0.1 does not do

- Only `audio.transcribe` and `text.generate`. Pictures, video and other skills show as "none of your sources can do this"; a required one cannot be allowed.
- Several models for one site (CONTRACT.md section 3.3) and its limits (section 3.4) work for `text.generate` only: the site names what it wants, the visitor ticks which of his models it gets (programs on his PC, OpenRouter, or his own keys at OpenAI, Anthropic, Google, MiniMax, DeepSeek, xAI, Z.ai (also its Coding Plan address), Mistral or another OpenAI-style service), and a call names one by its code. The wallet never swaps one model for another. Streaming reaches a site only over the direct link.
- No subscriptions or connected accounts, no provider account manager, no tests or quality signals, no purpose judge (the hook stays empty), no per-hour budgets, no visitor conditions in words. A visitor may add an OpenAI-compatible home server, but it is labelled "another computer (host)" and is not treated as a local model.
- "Over the budget" (`ask`) is not asked in the middle of a session: the call fails and the visitor raises the budget in the settings.
- Windows only (DPAPI, the tray, the registry). The engine itself has no Windows dependency except the secret store.
- Sessions do not survive a restart of the wallet.
- No streaming; one clip per call.
- The direct link does not go through a proxy (the address check needs the site's real address).

## 8. Security notes

- **Threat model.** A program running as the visitor is fully trusted. It can read the settings and the activity log, decrypt `secrets.dat` (its entropy string is in this public source), change the settings, and talk to the wallet's pipes as the visitor's own tools do. **The wallet cannot defend against it.** The rest of this section is about the other parties. For a polite agent that uses the MCP tools, the wallet keeps its promises: no tool returns a key; Full access gates the tools that see or change sites, limits and built-in sources; no tool allows a site, approves a paid call or approves another agent; and a new agent needs the visitor's Allow in a window. For web pages, other Windows accounts, a stranger's site and accidents, the wallet protects the visitor: a page reaches the wallet only through the extension, which stamps the origin, or through a link the visitor clicks; the pipes and DPAPI belong to one Windows account; grants, limits, blocks and the visitor's consent bound each site; and budgets, paid calls that ask first and the activity log limit the damage.
- **Origin.** It comes from Chrome (`sender.origin` of a top frame in a tab), never from the page; grants are bound to it, and another origin's call with a stolen grant id gets `{ ok: false }`. Pages in iframes are not served in 0.1.
- **The click rule.** The isolated-world script reads `navigator.userActivation.isActive` itself; the page cannot set it. A page can still call `request` in the few seconds after any click on it; that is the browser's definition of a user gesture.
- **The same "no".** Declined, blocked, no fitting model, no answer, wallet not running, limits and errors all reach the page as `null` or `{ ok: false }`. A blocked site gets its `null` without a notice, like a visitor without a wallet. Timing still differs between "answered at once" and "the visitor pressed Decline"; a page can tell that a person looked, not what they chose.
- **Who can talk to the wallet.** The native host accepts only this extension's ID. The MCP pipe is per user and opened with `CurrentUserOnly`; it accepts only a client image named `byoa-mcp.exe` in the wallet's install folder (or the test folder named by `BYOA_WALLET_MCP_PATH`). The wallet gets the client PID from the pipe handle and resolves the client and its parent itself. The agent id is the observed parent image path, not the hello name or path; if the parent cannot be resolved, the client image path is used and the consent says “unknown parent”. The consent shows the observed parent path so the visitor can judge it. A program of the same Windows user can still launch this bridge itself, so this is not a boundary against a compromised same-user program. Old agent records made from announced hello data stop matching after this change and the visitor is asked once to approve the observed identity again.
- **Agent endpoint confirmation.** Agent-supplied endpoints on another computer, and loopback ports other than the standard LM Studio `1234` and Ollama `11434` ports, are not saved, scanned, or contacted until the visitor confirms them. The window shows the canonical punycode host and port, the addresses seen in its one DNS check, and whether HTTP is not encrypted or HTTPS is encrypted. A confirmed remote endpoint is the visitor's own `home-server` for routing, so a `local-only` manifest may use it; at use time a named endpoint is resolved again and unsafe or public/private-drifting addresses are refused. MCP health checks expose only state, answer status, model count, latency and HTTP status for agent-added endpoints, never their answer text or model names.
- **Observed agent identity.** Approval is by the program that started the bridge. Another program of the same Windows user that starts the bridge through the same parent program inherits that approval, including Full access, without another window. This is the same trust as the visitor's own session. An unresolved parent is connection-only; general-purpose interpreters and shells are called out in the consent and do not offer Full access on their first connection. Old records based on hello data stop matching and are approved once for the observed identity.
- **Keys.** Stored with DPAPI for the current user and an extra entropy string. The string is in this public source, so it is no secret: DPAPI keeps the file from other accounts, not from a program running as the same user. The key is decrypted only for the moment a request needs one; never shown, logged or sent anywhere except to their own provider. Error messages from the provider carry only the HTTP status. `request_api_key_entry` is the no-Full-access path: the visitor types or replaces the key in the wallet. `set_api_key` always requires Full access because the value came through the agent.
- **Answers are user input.** The wallet trims and length-limits the text (128,000 characters) but does not sanitise it; pages must treat it like anything a visitor types.
- **Input limits.** Frames up to 8 MB, audio up to 6 MB, text messages up to 128 and, by default, 100,000 characters (the visitor's limit for the site, at most 400,000), answers up to 128,000 characters, manifests up to 64 KB; the WAV reader refuses anything it does not understand, and checks chunk sizes in 64-bit arithmetic (a chunk that claims to run past the end of the clip is bad audio, not an overflow). The site keeps at most as many calls in flight as the wallet's `maxParallelCalls` says (8 by default, at most 32; 4 for an older wallet) and may queue only a bounded number; the wallet refuses beyond that.
- **The wallet holds no model and downloads none.** Models run in programs the visitor installs and starts (the Llama app, LM Studio, Ollama, any OpenAI-compatible server). The wallet reads a program's list of models (the runtime scanner), sends it requests over its local address (or a confirmed home server) and deletes no file. Wallets of earlier versions that kept models in `BYOA\wallet\models` or `BYOA\models` leave them where they are; nothing reads them any more. What goes to the program is the audio of the call (speech) or the messages of the call (text), exactly as the call carried them; the wallet adds only its instruction about the language.
- **Registry.** Only the two native host keys and the `bringyourownagent` scheme key under HKCU, written by `install.ps1` and removed by `uninstall.ps1` (which also removes the one Startup shortcut `install.ps1 -StartWithWindows` made, and no other file).
- **The direct link.** Before the visitor's Allow nothing leaves the wallet, so a site cannot learn whether a wallet is installed or whether the visitor declined. Session codes are single use and short-lived because a link may reach another program that registered the scheme later. The second process that hands a link to the running wallet waits at most a few seconds for each step. The pairing token lets its holder use the visitor's AI on that one site, within the same grant and limits; it is kept like a key (DPAPI) and only under "decide on my own". A same-user program can hand the wallet a link over the pipe, which is no more than it could do by starting the wallet with that link; the visitor still sees the notice and the consent, even when the site already has "decide on my own".
- **A program that is not running, or no longer offers the model,** is skipped by the route with that reason ("not running", "model not found") until the scanner sees it again (every 30 s); calls fall back to the next source. A program that answers with an error is not marked broken: the error is shown in the source's state and in the Test result.
- **Logs.** The activity log keeps no audio and no text. Crashes go to `errors.log` with exception types and stacks only.

## 9. What the libraries and the spec need next

Found while building 0.1:

1. **Daily and hourly budgets** in the grant (the vision has them; the rules have only `perSession`). The wallet enforces its own per-day limits outside the gate for now.
2. **Receipts** in the spec. The contract's receipt (`cost`, `provider: "local" | "api-key"`) uses provider words that differ from the rules' provider kinds (`local-model`, `home-server`, …).
3. **Typed documents in the .NET library**: builders for grant, call and state, so a wallet does not write their JSON by hand, and the effective limits exposed for display.
4. **Reservations**: the execution contract asks wallets to reserve the slot and the estimate before a call and settle afterwards; a small helper in the libraries would make every wallet do it the same way.
5. **Skill parameters** (`languages` for `audio.transcribe`) are not checked by the rules, but the wallet routes on them; the first skill parameters deserve rules of their own.
6. **"Asking for more"** needs a definition in the spec (which changes count: new skills, higher expected cost, new languages?). 0.1 counts new skills it can serve, required skills it cannot serve, and an expected cost per session above the visitor's budget.
7. The contract's extension-host messages say nothing about the payload shapes or about a status message; section 2 above documents what 0.1 uses.
8. **Readiness**: the contract has no "preparing" state, so the wallet holds `request()` until its first usable route source is loaded and shows the visitor a progress hint in its own window. A progress hint in the page API would let sites show their own "preparing" instead of waiting without knowing why.

## 10. Transports

A site reaches the wallet in one of two ways. Both end in the same engine: the same notice and consent, the same
grants, blocks, "decide on my own", budgets, daily limits, gate, routing, fallbacks, "ask before paid", models ready
before the answer, and the same activity log. Grants and decisions belong to the origin, so a site allowed through
one transport is allowed through the other.

| | Extension (CONTRACT.md) | Direct link (CONTRACT-DIRECT.md) |
|---|---|---|
| The visitor needs | the browser extension | nothing in the browser; the wallet registers a URL scheme |
| The page starts it with | `window.byoa.request(manifest)` in a click handler | a click on a `bringyourownagent://connect?...` link (a browser launches a protocol only after a click) |
| The manifest comes from | the page | the link itself (base64url, at most 4096 bytes); the site's welcome echoes it |
| Calls come from | the page, through the extension and the native host | the site's server, over the wallet's own WebSocket |
| Identity | Chrome's `sender.origin` | TLS: the origin `https://host[:port]` of the `wss://` endpoint |
| Activity | as before | every entry marked "via link" |

### The direct link

- **The link.** `bringyourownagent://connect?v=0.1&endpoint=<wss URL>&manifest=<base64url of the manifest JSON, no padding, at most 4096 bytes decoded>&session=<code>` (CONTRACT-DIRECT.md with its §7). The scheme is `bringyourownagent`, never `byoa` (a generic name another program could take; on Windows the last program to register a scheme gets its links).
- **No contact before Allow.** The wallet makes no network request of any kind before the visitor's Allow (or the silent "decide on my own" grant of a reconnect): the manifest comes in the link, so not even a DNS lookup of the site happens. Decline, Block, a closed notice and a visitor without a wallet all look the same to the site: it never hears from the wallet. (An earlier form fetched the manifest before the consent; an external review showed that this told the site a wallet was installed, so the contract was changed.)
- **Registration.** `install.ps1` writes `HKCU\Software\Classes\bringyourownagent` ("URL Protocol"; `shell\open\command` = `"<wallet exe>" --url "%1"`); `uninstall.ps1` removes exactly that key, and only while its command is still this wallet's. A link starts the wallet; when the wallet is already running, the new process hands the link to it over the per-user pipe and exits. The native host may also relay a link frame from the browser, preserving the browser's `userActivation` bit; the command-line hand-off defaults to an activated browser link.
- **Checks before anything else.** The endpoint must be `wss://`; no user name, no fragment, no IP literals (in any spelling), no `localhost`, `.localhost`, `.local`, `.home.arpa`, `.internal`, `.lan` or single-label names. The manifest must be base64url without padding, at most 4096 bytes, a JSON object, and a valid manifest under the draft rules (the .NET library's `Manifest.Validate`). The session code is 22 to 256 URL-safe characters (at least 128 bits). A link that fails any check, repeats a code seen in the last 10 minutes, or belongs to a blocked site does nothing but leave an activity entry: no notice, no request. At most 4 links are acted on at once; more are ignored (a program flooding the wallet with links).
- **Addresses.** The WebSocket connection, after Allow, resolves the host itself and refuses it if any address is private, loopback, link-local, carrier-grade NAT, multicast or another special range (also inside IPv6: mapped, NAT64, 6to4, Teredo); it then connects to an address it checked, so DNS cannot change the answer in between. No proxy, no cookies, no redirects. Such a refusal is final; a connection that fails for network reasons is tried again with backoff while the session code may still be valid (60 s after the link), until the site answers `error`.
- **The developer switch.** `BYOA_WALLET_DEV_LOCAL=1` (tests only) also allows `ws://localhost`; the origin is then `http://localhost:<port>`, the same as an extension page there.
- **The consent.** The usual notice and consent, from the link's manifest, every time: also for an allowed site with "decide on my own" (only the difference when it asks for more). Only a reconnect with the stored pairing is granted silently under "decide on my own". A link-origin consent says "came by a link: confirmed after you allow"; only the extension path, where the browser vouches for the origin, says "verified". A visitor's Allow on a link is held in memory until the site's welcome echoes the link's manifest; a Decline or Block chosen on a link is not stored, so the site is asked again by its next link or request (CONTRACT-DIRECT.md §3).
- **The channel.** After the grant, and after the routed models are loaded, the wallet connects and sends `hello` (the session code, the wallet, the granted skills and the grant's expiry). The site answers `welcome` (with a pairing token and the manifest it put in the link) or `error` and a close. The welcome's manifest must be the link's, byte for byte, and only that echo stores the visitor's answer to the link. Otherwise the wallet says `bye`, closes, drops the held answer, and notes "the site's manifest differs from its link" in Activity; it does not revoke the site, since any link can name any site. Then the site sends `call` frames and the wallet answers `result` frames: the site keeps at most as many calls in flight as the hello's `limits.maxParallelCalls` says (4 when it says none) and may queue a bounded number; the wallet refuses the next one as a backstop. The hello also carries the limits the site is held to and, if the site asked for several models, the models it was given; a `grant` frame repeats them when the visitor changes them, and a streamed call (`params.stream`) is answered with `chunk` frames before its `result`. The wallet accepts frames of up to 4 MB from the site; its own frames stay below 1 MB (the largest is a text answer, 128,000 characters), and a site must accept at least 1 MB from it. A frame that is not a JSON message, or a site that speaks before its welcome, closes the connection; unknown frame types are ignored. The wallet sends `{"type":"ping"}` every 30 s, and WebSocket pings that end a connection whose site stopped answering. `bye` from either side ends it.
- **Pairing.** The welcome's token must be 22 to 1024 characters from `A-Z`, `a-z`, `0-9`, `_` and `-`; it is kept (DPAPI, `pairings.dat` in the data folder) only for a site with "decide on my own". It is stored with the manifest the visitor agreed to. With it the wallet reconnects after a dropped connection (backoff 1, 2, 5, 10, then 30 s) and after its own restart, with `hello` carrying the pairing instead of a code and no notice, under a silent grant from the stored manifest. The welcome then carries the site's current manifest: within what the site is allowed it is taken silently; if it asks for more, the wallet says `bye`, closes and forgets the pairing, and the site needs a new link, where the consent shows only the difference. A grant that ends (12 hours) is renewed the same way. Without the token, a dropped connection stays closed.
- **Revoke and Block** in the wallet say `bye`, close the site's connections and forget its pairing. Turning "decide on my own" off ends the reconnecting at the next attempt. **Pause** (by hand in Sites, or by the wallet after the site goes unused for the time set there, a day by default) closes the connections the same way, forgets the pairing and stops the reconnecting; the site comes back only through a new link, after a click, with the consent window's **Resume**.
- **What the visitor sees.** Sites shows "Connected without the extension" (and "paired" when the wallet will come back on its own); Activity marks the link's events (link ignored, connected, closed, refused) and every request and call "via link".

## 11. Registry, MCP and agents

Preparation is a real wait, not an unbounded page timeout. After Allow (or a silent reconnect) the wallet makes the first usable local source of each granted skill do its simplest job once for real, and keeps the request pending until that is done: speech to text transcribes a clip of 3 seconds (silence), text generation writes one short answer, and an image model would draw the smallest image it can. That loads the model, so the site's first real request does not wait for it, and it shows that the model can do its job at all; a model that fails the job gives its place to the next local fallback. The job starts while the visitor reads the consent, and one job per source is shared by all languages. The wait ends after three minutes at the longest; for a link it ends about 100 seconds after the link came, so the wallet still connects with the link's one-time code (valid 120 seconds). The switch "Check the models when a site connects" (Sources page, `WarmUpOnConnect` in settings.json) is on by default; turned off, nothing is run at connect or at start, and the first call meets a cold model. A slow preparation shows the "Preparing your model…" toast and then returns a grant whose first call can use a ready fallback or say "AI unavailable". It does not hold requests from other sites.

The wallet has one registry for sources and routes. The Sources page, Help, and the MCP bridge read and change that registry, so an agent sees the same source ids, language chains and activity that the visitor sees in the wallet. Added sources can be edited, disabled, reordered and removed; built-in sources can be disabled only with Full access when an agent asks. An agent may add a loopback source directly. An endpoint on another computer is shown to the visitor with its full host, model, and encryption state; nothing is saved, scanned, or contacted until the visitor allows it. The confirmation is remembered for that source id and endpoint. An added source serves one skill (`text.generate` or `audio.transcribe`); the speech skill's source ids end in `#transcribe`, so the same model can be added once for each skill. The wallet never downloads or deletes a model. The action is logged with the actor.
`byoa-mcp.exe` is a stdio JSON-RPC 2.0 MCP server (protocol revision `2025-06-18`). It does not start the wallet. It connects to a per-user named pipe whose name includes the active `BYOA_WALLET_HOME`, and the wallet creates the pipe with `CurrentUserOnly` and at most eight connections. The bridge keeps no settings, model files or secrets. The first connection shows the announced display name and the parent path observed by the wallet. The visitor can Allow, Not now, or Block; an approved observed identity reconnects silently until revoked. “Not now” is remembered for 60 seconds. Old pre-observation records do not match and are approved once again.

Without Full access, `status` contains connected-site counts only and `activity` replaces origins with stable `site-xxxx` labels and drops free-text notes. Full access is off by default and can be changed in Settings → Managing agents; the wallet still owns visitor consent and an agent cannot manufacture it by calling a tool.

Agent-added endpoints on another computer, and loopback ports other than standard LM Studio `1234` and Ollama `11434`, are not saved, scanned, or contacted until the visitor confirms them. The confirmation window shows the canonical punycode host and port, the addresses seen in one DNS check, and whether HTTP is not encrypted or HTTPS is encrypted. A confirmed remote endpoint is the visitor's own `home-server` for routing, so a `local-only` manifest may use it; use-time DNS checks still refuse unsafe or public/private-drifting addresses. Agent health checks return only state, answer status, model count, latency and HTTP status, never model answers or model names.

API keys are write-only. `request_api_key_entry` opens a field in the wallet so the visitor enters or replaces the key; the agent sees only the saved result. `set_api_key` always needs Full access because the value was supplied through the agent. Neither path returns the key, and Activity records only that a key was saved. Help articles are embedded once in the core assembly and are rendered by the Help window and returned by the MCP `help` tool.

Measured on the development machine with the end-to-end test (`wallet/tests/e2e/direct_e2e.py`, fake sites on `ws://localhost` that count every request they get): no request reaches a site before Allow; link to notice 1.2-3.0 s with the wallet starting cold; Allow to `hello` 4.7 s (the model asked to load first, 0.2 s, because the program already had it); calls round trip from the site's server 183-335 ms in Russian, answered by Qwen3-ASR in the Llama app; a restarted wallet back on the connection 1.9 s after it starts. In an earlier build, with the speech engines inside the wallet, the Geo-1 game run locally (its direct mode, no extension in the browser, the manifest in its link) saw: a page reload binds the same connection again; a restarted wallet is bound again 3.4-3.6 s after it starts; every welcome echoed the link's manifest. A real click in a headed Chromium shows Chromium's own prompt ("Open <the app>?", with the exe's description, "Agent wallet", once Windows has not cached an older name) and then the wallet's notice; that second process hands the link to the running wallet over the pipe.
